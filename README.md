# Data Modeling for Service Systems

Проект посвящён переходу от пользовательских и функциональных требований к структуре данных информационной системы.

В общей серии проектов рассматриваются две предметные области:

- система онлайн-записи в барбершоп;
- сервис доставки заказов.

Для обеих систем важны пользователи, роли, бизнес-объекты, жизненные циклы сущностей и связи между данными.

Детальная логическая модель в этом репозитории разработана для системы онлайн-записи.

## Контекст предметных областей

### Онлайн-запись

Система должна хранить информацию о:
- клиентах;
- сотрудниках;
- ролях сотрудников;
- услугах;
- услугах конкретных мастеров;
- расписании и временных слотах;
- бронировании;
- уведомлениях;
- скидках.

### Доставка

Во втором сквозном кейсе аналогичный подход к моделированию может применяться к:
- пользователям и ролям;
- заказам;
- бронированию заказа;
- доставкам;
- статусам;
- поставщикам;
- начислениям;
- переназначениям.

Таким образом, проект демонстрирует общий подход к преобразованию функциональных требований в логическую структуру данных.

## Что было сделано

На основе пользовательских сценариев были определены объекты системы, их назначение, атрибуты и связи.

Для атрибутов рассматривались:
- тип данных;
- PK / FK;
- обязательность;
- длина строковых значений;
- возможность NULL;
- ограничения уникальности;
- назначение поля.

Также были определены связи между сущностями и их кратность.

## Основные сущности модели

### `Person`

Общая сущность физического лица.

Пример атрибутов:
- `id`;
- `login`;
- `password_hash`;
- `name`;
- `phone`;
- `registration_date`.

### `Client`

Расширяет данные персоны для пользователя-клиента.

Связан с:
- Person;
- TimeSlot;
- Discount;
- Notification.

### `Employee`

Хранит данные сотрудника системы.

Через дополнительные таблицы сотруднику назначаются роли и оказываемые услуги.

### `EmployeeRole`

Позволяет назначать сотрудникам роли, например:
- мастер;
- менеджер.

### `Service`

Справочник доступных услуг.

### `MasterService`

Связующая сущность между сотрудником и услугой.

Она позволяет реализовать отношение many-to-many:

один мастер может оказывать несколько услуг, а одна услуга может выполняться несколькими мастерами.

### `TimeSlot`

Основной объект расписания.

Содержит:
- дату;
- время;
- мастера;
- клиента;
- услугу;
- статус;
- время бронирования.

До бронирования ссылки на клиента и услугу могут отсутствовать.

### `Discount`

Хранит скидки клиента:
- процент;
- период действия;
- описание;
- признак активности.

### `Notification`

Хранит информацию об уведомлении:
- клиент;
- канал;
- сообщение;
- время отправки;
- статус.

## Командная работа

Проект выполнялся командой.

Моя роль — **Team Lead**.

## Результат

Проект показывает переход:

`Use Cases → сущности → атрибуты → ключи → связи → логическая модель данных`

Модель может использоваться как основа для дальнейшего проектирования реляционной базы данных и обсуждения реализации с разработчиками.

### Использованные подходы

`Data Modeling` · `UML Class Diagram` · `ER Modeling` · `Data Dictionary` · `PK / FK` · `Cardinality` · `Relational Model`
